## 1. 背景

### 1.1 现状分析

当前 L2-A 打分系统：
- ✅ 已实现：3 因子评分模型（momentum_20, inv_volatility_20, turnover_rate）
- ✅ 权重固定：0.5 / 0.3 / 0.2（启发式设定）
- ⏳ Phase 1（进行中）：验证基础模型可用性
- 🔮 Phase 2（待规划）：因子优化与扩展

### 1.2 瓶颈

| 维度 | 问题 | 影响 |
|------|------|------|
| **因子评估** | 手工逐一回测，每个因子 2 小时 | Phase 2 无法快速迭代 |
| **权重优化** | 无数据支撑的初始权重 | 模型效能可能不是最优 |
| **因子组合** | 无法系统性评估多个因子组合 | 遗漏最优组合 |
| **相关性控制** | 因子间冗余无法快速检测 | 权重浪费、风险敞口不均 |
| **报告生成** | 评估结果手工编写 | 易出错、难追溯 |

### 1.3 机遇

- ✅ CLI 工具已就绪：`hf factor health`, `hf factor correlation`, `hf backtest run`
- ✅ AI 可调用白名单命令（CLAUDE.md）
- ✅ 量化结果可追踪：IC、Sharpe、最大回撤、相关性矩阵

## 3. AI 能力清单

### 3.1 明确能做的（✅ 已验证可行）

#### **3.1.1 因子有效性分析**

**任务**：评估单个因子的投资能力

```bash
# 调用 CLI
hf factor health --factor momentum_20 --lookback 250

# AI 可做的分析
- 提取 IC（信息系数）、Sharpe、最大回撤
- 对比多个时间窗口的稳定性
- 生成评估报告（格式化表格）
- 标记："✅ 有效" / "⚠️ 边界" / "❌ 无效"
```

**适用场景**：
- 评估新因子（max_drawdown_60, trend_stability_20 等）
- 定期健康检查（每个因子是否仍有效）
- Phase 2 因子库维护

**输出格式**：
```json
{
  "factor_name": "momentum_20",
  "ic": 0.12,
  "sharpe": 1.5,
  "max_drawdown": 0.25,
  "status": "✅ Effective",
  "recommendation": "Keep in portfolio, weight 0.5 suggested"
}
```

#### **3.1.2 因子相关性分析**

**任务**：检测因子间的冗余关系

```bash
# 调用 CLI
hf factor correlation --factors momentum_20,inv_volatility_20,turnover_rate,max_drawdown_60

# AI 可做的分析
- 生成相关性矩阵
- 标记高相关对（>0.7）→ 预警冗余
- 推荐权重调整（降低相关因子权重）
- 聚类分析（哪些因子属同一"维度"）
```

**输出格式**：
```
相关性矩阵（去冗余分析）：

                  momentum inv_vol turnover max_dd
momentum            1.00    0.15    0.22    0.68 ⚠️
inv_vol            0.15    1.00    0.05    0.12
turnover           0.22    0.05    1.00    0.08
max_dd             0.68 ⚠️  0.12    0.08    1.00

发现：
- momentum & max_drawdown 相关 0.68（偏高，可能冗余）
- 建议：降低 max_drawdown 权重，或用 max_dd/momentum 的主成分替代
```

**适用场景**：
- Phase 2 新增因子前的冗余检查
- 权重配置优化
- 投资组合风险敞口均衡

### 3.2 可能能做的（⚠️ 需探索）

#### **3.2.1 因子组合优化**

**概念**：在众多因子组合中，找到最优的组合与权重

**技术方案**：
```
方案 A（穷举法）：
- 枚举所有因子组合（2^n）
- 逐一回测
- 排序结果
- 缺点：组合数爆炸（10个因子 → 1024 种）

方案 B（启发式搜索）：
- 从 baseline 开始，逐个尝试加/减因子
- 评估增量 Sharpe
- 贪心地保留最优操作
- 缺点：可能陷入局部最优

方案 C（蒙特卡洛模拟）：
- 随机采样 100 个权重配置
- 回测每个配置
- 关键部分微调
- 缺点：不保证全局最优
```

**当前状态**：
- ❌ Phase 1 不做（工作量大）
- 🔮 Phase 2 可探索（如果因子数 < 8）

**前置条件**：
- 因子库稳定（>3 个因子）
- 回测性能足够快（<30 分钟/配置）

**概念**：监测因子的健康度变化

```
监测指标：

- 相关性上升（从 0.4 → 0.8）→ 预警

```

**频率**：
- 日级：每日检查（快速）
- 周级：每周深度评估（完整）
- 月级：月度总结（对标）

**输出**：
```
因子健康度周报（2026-04-02）：

momentum_20：
  - IC: 0.12 (周环比 -5%) ✅
  - Sharpe: 1.5 (周环比 -8%) ⚠️ 需关注
  - 缺失率: 1.2% (周环比 +0.3%) ✅
  
inv_volatility_20：
  - IC: 0.08 (周环比 +12%) ✅
  - Sharpe: 1.2 (周环比 +5%) ✅
  
[后续决策不做，仅作监控]
```

**应用场景**：
- 定期（周/月）的因子健康检查
- 异常及时发现与通知
- 因子衰退时的早期预警

---

### 3.3 明确不能做的（❌ 约束）

根据 CLAUDE.md 的 G3 执行安全条款：

| 不能做 | 原因 | 如果做会怎样 |
|--------|------|-----------|
| **自动修改权重** | 参数变更需 G3 批准 | 可能误伤线上模型 |
| **自动上线新因子** | 新因子需回测 + 审批 | 违反审计链路，数据被污染 |
| **基于 web_search 决策** | web_search decision_weight=0 | 外部舆情误导决策 |
| **直接调用交易接口** | AI 无权限访问 | 安全风险 |
| **跳过人工审核** | 所有参数变更需人审 | 无人工制衡，容易出错 |

**核心约束**：
> **"AI 可以提议，但不能决策；可以分析，但不能执行；可以建议，但不能生效。"**

## 6. 技术实现建议

### 6.1 架构

```
AI System (Claude)
    ↓
Skill: factor-optimizer
    ├─ factor_health_task()     → hf factor health
    ├─ correlation_task()       → hf factor correlation  
    ├─ backtest_task()          → hf backtest run
    ├─ weight_optimization()    → IC/Sharpe 优化
    └─ report_generation()      → Markdown 报告
    ↓
存储：docs/analysis/factor_optimization/
    ├─ evaluations/             （单因子评估）
    ├─ correlations/            （相关性分析）
    ├─ backtests/               （回测结果）
    └─ recommendations/         （权重推荐）
    ↓
G3 Flow（人工审批）
```

### 6.2 数据流

```
INPUT（人工）：
- 候选因子列表 + 定义
- 回测期间（如 2024-01-01:2026-04-01）
- 业务约束（如 max_drawdown 权重 ≤ 0.3）

PROCESSING（AI）：
- 并行调用 CLI × N 个因子
- 收集、解析结果
- 计算对比指标
- 生成权重方案

OUTPUT（自动生成）：
- 因子评估表（10 维）
- 相关性矩阵
- 回测对比表
- 权重推荐（A/B/C 方案）
- Markdown 报告 + Excel 附件
```

## 7. 约束与合规

### 7.1 G3 执行安全

**核心原则**（摘自 CLAUDE.md）：

> "参数变更、阈值变更、实盘发布必须走审批流——AI 提出的变更不得自动生效。"

**应用到因子优化**：

```
✅ AI 可以：
□ 建议权重：0.4 / 0.2 / 0.2 / 0.2
□ 提出新因子方向
□ 预警相关性冗余
□ 评估因子有效性

❌ AI 不能：
□ 直接修改 SCORE_PROFILES
□ 自动上线新权重到线上
□ 跳过人工审核
□ 基于 web_search 的舆情影响权重
```

### 7.2 审计链路

**要求**：每个因子决策都必须可追溯

```
决策审计链路：

2026-04-15 投资研究团队 提出 max_drawdown_60
    ↓
2026-04-15 AI 自动评估
    报告：IC=0.12, Sharpe=1.8, 相关性 0.68 vs momentum
    输出地址：docs/analysis/factor_optimization/evaluations/max_drawdown_60_2026-04-15.md
    ↓
2026-04-16 投资主管 人工审视
    决议：同意纳入，权重 0.2
    审批：PO 签名 + 时间戳
    ↓
2026-04-17 风控组 合规审查
    风险评估：max_drawdown 权重 0.2 可接受
    批准：风控主管 签名
    ↓
2026-04-18 工程实现
    代码修改：SCORE_PROFILES["l2-score-v1.1"] 加入 max_drawdown
    Code Review + Test + 灰度
    ↓
2026-04-20 全量上线
    上线信息：版本 l2-score-v1.1，包含 max_drawdown
    监控：每日健康度检查
```

**可追溯性工具**：
- 所有报告存储在 git 版本控制中
- 每个决策都有时间戳 + 签名
- 可回溯："为什么选择 max_drawdown_60？" → 找到评估报告

### 11.3 术语表

| 术语 | 定义 |
|------|------|
| **IC** | 信息系数（Information Coefficient），衡量因子与排名的相关性，范围 [-1, 1]，越高越好 |
| **Sharpe** | 夏普比率，收益/风险比，越高越好（通常 >1.0 为优秀） |
| **相关系数** | 两个因子的线性相关程度，> 0.7 时认为有冗余 |
| **权重** | 因子在最终评分中的贡献比重，所有权重和 = 1 |
| **G3** | 执行安全层（Governance Level 3），涉及参数变更、审批流 |
| **回撤** | 从最高点到最低点的亏损幅度，衡量下行风险 |
