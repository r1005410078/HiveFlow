# MVP 需求

## 文档目的

这份文档用于定义 HiveFlow 第一版最小可行产品的范围。

第一版的目标不是做一个完整的智能投资系统，而是先把最关键的地基搭起来，验证 HiveFlow 作为个人资产决策系统是否成立。

## MVP 目标

HiveFlow 第一版要先完成一件事：

建立一个可信的资产决策底座，让用户可以在同一个系统里查看真实状态、比较策略目标、识别风险水位，并记录自己的决策和修正。

## MVP 要解决的核心问题

第一版只聚焦解决下面这些问题：

1. 当前有哪些标的值得看
2. 当前每一支持仓危险不危险
3. 当前更该信哪个策略
4. 当前实际持仓和策略目标差多少
5. 当前整体资产配比是否失衡
6. 当前最该先处理哪一部分仓位和资金

如果某个功能不能直接帮助用户解决这些问题，就不进入第一版。

## MVP 必做功能

第一版必须具备下面这些能力：

1. 管理可用策略和基础回测结果
2. 记录真实持仓和账户状态
3. 查看当前每一支持仓及其风险水位
4. 查看当前整体资产配比
5. 生成当前策略目标持仓
6. 对比实际持仓与当前策略目标持仓
7. 给出调仓、资金分配和处理优先级建议
8. 记录用户的确认、修正和关键偏好

## MVP 必备底层模块

为了让这些功能成立，第一版至少要先有下面这些底层模块：

- 策略池
- 策略席位
- 基础回测结果
- 持仓状态
- 单标的风险水位
- 资产配比状态
- 当前策略目标持仓
- 调整建议生成
- 决策日志
- 用户偏好记录

## MVP 第一版策略席位

第一版先不做复杂的多 Agent 协作，但会先为后续打下席位结构基础。

建议第一版先固定 3 个策略席位：

1. `进攻席位`
   负责承接高弹性、高波动、偏进攻型资金
2. `防守席位`
   负责承接防守资金、低风险仓位和缓冲仓位
3. `长期席位`
   负责承接长期持有和低频调整的资金

第一版里，策略席位先只做三件事：

- 表达资金用途
- 限定可使用的策略范围
- 承接对应资金占比

第一版不要求席位自己自主决策，也不要求席位之间自动协同。

### 1. 进攻席位

进攻席位用于承接高弹性、高波动、以争取更高收益为目标的资金。

它的默认特点是：

- 更关注机会和收益弹性
- 更能接受波动
- 调整频率可以更高

它更适合承接这类策略：

- 趋势突破
- 动量轮动
- 高弹性机会策略

### 2. 防守席位

防守席位用于承接保护性资金和缓冲资金。

它的默认特点是：

- 更关注回撤控制
- 更关注风险水位
- 更强调仓位收缩和防守配置

它更适合承接这类策略：

- 防守轮动
- 低风险配置
- 现金 / 稳定币防守策略

### 3. 长期席位

长期席位用于承接低频、长期持有导向的资金。

它的默认特点是：

- 更少频繁调整
- 更关注长期配置合理性
- 更重视长期持有逻辑

它更适合承接这类策略：

- 长期持有增强
- 低频趋势配置
- 长周期配置策略

## MVP 当前不做

第一版明确不优先做：

- 自动交易
- 自动下单
- 高频交易相关能力
- 复杂多 Agent 协作
- AI 自动生成策略
- AI 自动调优闭环
- 复杂版本管理
- 大而全的多市场覆盖
- 界面和交互形态的过早细化

第一版统一只做建议、记录和对比，不直接进入执行环节。

无论后续是股票、虚拟币，还是不同交易通道，执行方式的差异都放到后续版本再展开。

## MVP 成功标准

如果第一版能让用户稳定做到下面这些事情，MVP 就成立：

1. 能快速查看真实持仓、风险水位和资产配比
2. 能清楚看到当前策略目标和实际持仓的差异
3. 能拿到明确的调仓、配比和优先级建议
4. 能把自己的偏好、修正和决策记录沉淀进系统
5. 重新打开系统时，不需要从头解释自己的状态和背景
