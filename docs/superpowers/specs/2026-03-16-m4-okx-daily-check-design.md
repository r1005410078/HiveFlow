# M4 重新定向：OKX 接入 + 每日健康检查

**日期**：2026-03-16
**状态**：已通过用户确认

---

## 背景与问题

HiveFlow 当前架构以"策略驱动"为核心入口——用户必须先定义策略，才能使用持仓偏离、调仓建议等能力。但实际用户处于"靠感觉"阶段（尚未形成明确策略），且持仓在 OKX 上，当前数据只能手动导入 CSV。

这导致一个先有鸡还是先有蛋的问题：系统需要你有策略才能用，但你需要先用系统才能形成策略。

**用户真实需求**：每天一条命令，30 秒内知道——OKX 持仓还健康吗？要不要做决策？

**关键决策**：`check` 在 M4 阶段**只做风险层，不做偏离分析**。原因：目标权重必须有依据（来自回测结果），随意填写一个百分比没有意义，与"可追溯决策"的核心理念冲突。偏离分析在积累行情数据并跑过回测后的 M5 引入。

---

## 目标

> 让用户每天执行两条命令完成日常检查：
> 1. `hiveflow sync` — 从 OKX 拉取最新持仓和价格
> 2. `hiveflow check` — 输出各币种风险信号 + 一句话结论

## 能力一：`hiveflow sync`

### 设计原则

- **手动触发**，不做定时任务，用户自己决定何时同步
- 复用现有 `MarketBar` 模型存储价格，`Position` 模型存储持仓

### OKX API

| 数据 | 接口 | 鉴权 |
|---|---|---|
| 当前持仓 | `GET /api/v5/account/positions` | 需要 API Key |
| 当前价格 | `GET /api/v5/market/tickers` | 公开 |
| 历史 K 线 | `GET /api/v5/market/candles` | 公开 |

### 配置

API Key 存于 `.env`（已在 `.gitignore`），通过现有 `pydantic-settings` 读取：

```
OKX_API_KEY=xxx
OKX_API_SECRET=xxx
OKX_PASSPHRASE=xxx
```

### 命令

```bash
hiveflow sync                  # 同步持仓 + 当前价格
hiveflow sync --days 30        # 同步最近 30 天 K 线（用于风险计算，最大 365）
```

`--days` 接受正整数，锚定时区为 UTC，最大值 365。历史 K 线使用日线粒度（OKX `bar=1D`），满足 7 日回撤计算需求。

### 原子性与失败处理

`sync` 采用**全成功或全失败**策略：

- 持仓 API 调用与价格 API 调用均成功后，才写入数据库（单事务提交）
- 任一调用失败（网络超时、鉴权错误、限流）→ 不写入任何数据，输出错误原因，退出码 1
- 部分成功不可接受，避免持仓与价格时间戳错位
- 限流时失败即退出，不自动重试

### 错误输出示例

```
错误：OKX API 鉴权失败（401）。请检查 .env 中的 OKX_API_KEY / OKX_API_SECRET / OKX_PASSPHRASE。
错误：网络超时，请稍后重试。
错误：请求频率超限（429），请稍后重试。
```

### 成功输出示例

```
同步完成  2026-03-16 09:32 UTC
持仓：4 个币种  总估值：12,450 USDT
价格：4 条记录已更新
```

### Symbol 规范化

OKX 返回的 instrument ID 格式为 `BTC-USDT`。同步时统一截取连字符前的部分作为 `symbol`（即 `BTC`），与现有 `Position.symbol` 字段格式保持一致。仅处理现货（`instType=SPOT`），衍生品不在 M4 范围内。

### 价格写入语义

`MarketBar` 按 `(symbol, timestamp)` 做 upsert：相同时间戳的记录覆盖更新，不同时间戳追加，避免重复导入产生重复行。写入逻辑与现有 CSV 导入路径相同，不复用 CSV 校验管道，直接写入。

### 架构位置

OKX HTTP 客户端属于基础设施层：
`src/hiveflow/infrastructure/okx/okx_provider.py`（纯 HTTP 数据拉取，无业务逻辑）

应用层：`src/hiveflow/application/sync.py`
CLI：新增 `sync` 命令

## 能力二：`hiveflow check`

### 设计原则

M4 阶段 `check` **仅输出风险信号**，不做持仓偏离分析。偏离分析需要有依据的目标权重（来自回测），在 M5 引入。

### 风险指标

基于已同步的历史行情数据，计算：
- **近 7 日最大回撤**：以 7 日窗口内最高收盘价为基准，计算至最低收盘价的跌幅

### 告警阈值

| 指标 | 正常 | ⚠️ 注意 | 🔴 危险 |
|---|---|---|---|
| 7 日最大回撤 | > -10% | -10% ~ -20% | < -20% |

**结论判断规则：**
- 无任何告警 → "今天安全，无需操作"
- 1 个及以上"注意"，且无"危险" → "建议关注 XXX"
- 任意 1 个"危险" → "危险，建议处理"

### 输出示例

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  今日持仓健康检查  2026-03-16
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[结论] ⚠️  建议关注 — ETH 近7日回撤较大

风险信号（近7日最大回撤）
  BTC   -3.2%   正常
  ETH   -12.4%  ⚠️ 注意
  SOL   -8.1%   正常

建议动作
  → ETH 回撤偏大，留意是否触发止损线
```

### 退出码

`check` 命令始终以退出码 0 结束，无论结论是"安全"还是"危险"——结论通过输出文字传达，不通过退出码区分。

### 无历史行情数据时的降级行为

若用户未执行过 `sync --days`，风险层跳过，输出提示：
```
提示：未检测到历史行情数据，请先执行 hiveflow sync --days 30 以启用风险分析。
```

### 架构

新增 `src/hiveflow/application/health_check.py` 用例。
风险计算（回撤）作为新逻辑写入 `src/hiveflow/services/risk_engine.py`（当前该文件仅含优先级分类函数，需新增基于 `MarketBar` 数据的回撤计算逻辑）。
CLI 新增 `check` 命令。

## 未来演进路径（M5+）

当前（M4）：积累行情数据 + 风险感知 → M5 演进：

1. **目标权重来自回测**：跑几个不同配比的 `backtest`，找到认可的历史表现，以此为目标权重（有依据，不随意）
2. **`check` 加入偏离分析**：实际权重 vs 回测得出的目标权重
3. **`hiveflow history`**：回顾历史持仓变化曲线
4. 从固定权重逐步升级为"有条件的权重"→ 这才是策略 DSL 出现的时机

**原则**：策略 DSL 从真实使用中"长出来"，不是设计出来强加的。
